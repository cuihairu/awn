# 3D 座位图方案（P2）

- 日期：2026-10-15
- 背景与依据：`docs/research/venue-seatmaps.md`（调研已交 dde227b）、用户 2026-10-12 拍板（不立项 `venue-seats`；第一阶段 L1/L2 选区选排，不强求逐座；3D 定 P2，2D 过目后出方案）、2D 前端已落地（b607772：`apps/web/lib/seatmap.ts` + `components/SeatMap.tsx`）。
- 2D 过目状态：原型 `prototypes/web/seatmap-2d.html` 与实现均已代决完成（2026-10-14 巡检授权），本方案按既定顺序给出。

## 1. 定位与边界

- 3D 是 2D 座位图的**视觉增强层**，不是第二套交互面：选座、键盘、读屏仍走 2D 路径。
- 边界沿用 2D 口径：**座位图 = 空间与编号，库存 = 可售状态**。3D 只改变呈现维度，不引入新的交易语义。
- 素材红线不变：3D 场景用**几何线框占位**（分区多边形、排线、舞台基准块），不用场馆照片、贴图、航拍图或任何 logo 代餐。

## 2. 数据前提（决定走哪条路）

| 档位 | 数据状态 | 3D 能做什么 |
|---|---|---|
| A（现状） | `platform_seats`（V17）只有分区/排/座编号，无坐标 | 程序化网格 + 视角变换（2.5D），不声称场馆形状正确 |
| B（数据落地后） | 座位坐标或分区几何（L1/L2 数据，依赖挂起项拍板与三问验证） | 真 3D：分区多边形、排弧线、舞台定位、逐区朝向 |

坐标数据来源属挂起项（调研已交、待用户拍板 + 指定首批 5 场馆）；**本方案不以「能采到全国场馆数据」为前提**。

## 3. 分阶段方案

### S1 · 视角增强（无新数据、无新依赖，可与 2D 同期）

- 对现有 SVG 网格加 CSS 3D 变换（`perspective` + `rotateX` 倾斜），提供「俯视 / 透视」切换；舞台基准条与分区排布仍为程序化网格。
- 交互与无障碍完全复用 2D（`SeatMap.tsx` 的 `role="button"` / 键盘 / aria-label 不动）。
- 验收：同一 `SeatInput[]` 下俯视图与现状像素一致；透视图不新增交互路径；`prefers-reduced-motion` 下禁用过渡。

### S2 · 数据模型扩展（后端契约，坐标落地后）

- 座位坐标可选化：`platform_seats` 增坐标字段或独立坐标表（版本化，随三问验证「可复用、可校验、可版本化」口径设计）。
- 公开端点 `SeatView` 透出可选 `x`/`y`（或分区几何参数）；**`null` = 坐标缺失，前端回退 S1 网格**，不破坏现有 2D 契约。
- **落地记录（2026-10-18，S2 契约先行已代决，见 `venue-seatmaps.md` §8 #9）**：V27 `pos_x`/`pos_y` + `SeatView`/公开 `SeatMapItem` 可选 `x`/`y` + 前端 `SeatInput` 可选坐标（null 回退网格，消费逻辑未接）；契约条目进 `docs/api/contracts.md`。3D 渲染（S3）未动。

### S3 · 真 3D 原型（three.js 程序化，Web 端先行）

- 参考 Fi-Stadium（MIT）思路：`InstancedMesh` 逐座实例化 + `Raycaster` 拾取，万级座位单 draw call；**吸收设计思想，不引入其代码**。
- 场景内容：分区多边形壳、排弧线、舞台基准块；座位状态着色沿用 2D 三态（可选 / 置灰 / 选中）。
- 双轨结构：3D 画布只负责视觉与悬停提示；点击选中后同步 2D 层状态并聚焦，键盘/读屏始终在 2D 层。

### S4 · L1/L2 交互（依三问验证结论决定）

- 选区（L1）/ 选排（L2）粒度的 3D 呈现：分区高亮、票价分层着色、开放区域开关；逐座精确（L3）不在本期。
- Flutter 端：一期不做 3D（生态弱、优先级低）；若需要先出 CustomPaint 伪 3D 视角图，真 3D 另行评估。

## 4. 技术选型对比

| 方案 | 座位数上限 | 依赖 | 无障碍 | 结论 |
|---|---|---|---|---|
| CSS 3D 变换（S1） | 与 2D 相同（SVG 节点数受限） | 无 | 完全复用 2D | 采用（近期） |
| three.js WebGL（S3） | 数万（InstancedMesh） | 新增 three.js | 需并行 2D DOM 层 | 采用（S2 数据后） |
| Canvas 2.5D 自绘 | 数千~数万 | 无 | 需自建命中检测，成本高 | 不采用 |
| Flutter 3D | — | 生态未成熟 | — | 延后 |

## 5. 性能与降级

- 预算：DOM/SVG 座位节点 > 3 千即卡顿，S1 只做视角不改节点数；three.js 路径按 1.8 万座（国家体育场级）设计实例化。
- 降级链：WebGL 不可用或坐标缺失 → S1 透视图 → 纯 2D 俯视；每级都保留完整选座能力。

## 6. 验收口径（阶段化，满足才可勾选实现项）

1. S1：俯视/透视切换 + reduced-motion 尊重 + 交互回归全绿（现有 seatmap 11 例不降级）。
2. S2：契约条目进 `docs/api/contracts.md`；`null` 坐标回退路径有测试。
3. S3：3D 场景为几何线框；键盘选中一座的路径在 2D 层可用；1 万座渲染首帧 < 2s（开发机基线）。
4. S4：选区/选排状态与 2D 联动一致，无第三套状态源。

## 7. 未决依赖（不阻塞 S1）

- 场馆座位数据来源拍板（挂起项）；首批 5 个目标场馆名单（用户指定）；三问验证结论（决定 S4 与是否抽独立项目）。
