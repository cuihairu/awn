# 实施计划

不建议一次性把整个系统交给一个 Agent，要求它生成所有代码。更可靠的做法是：**先固定架构契约，再按阶段分配任务，并为每个阶段设定可验证的完成条件。**

## Phase 0：架构基线（已完成）

AWN Phase 0 的任务书全文如下，可直接作为首轮 Code Agent 的任务说明。

Phase 01–06 均已完成（代码 + 测试 + 文档）；当前处于收尾阶段：文档一致性审计、压测与部署手册。

### 项目目标

使用 Java + Spring Boot 构建模块化单体。系统包含活动与场次、票务商品、可配置专场、统一订单、库存预留、支付、退款、履约、卖家挂牌和票务情报。

### 不可违反的架构原则

1. 专场只负责展示和营销，不得创建独立的购买、库存、支付或退款实现。
2. 所有专场必须使用统一商品 API 和统一订单链路。
3. PostgreSQL 是交易库存的最终权威来源。
4. 库存预留必须使用数据库事务和原子条件更新。
5. 订单、库存预留记录和必要的 Outbox 事件必须在同一数据库事务中提交。
6. 支付回调、订单创建、库存释放和退款处理必须具有幂等性。
7. 支付成功与库存释放发生竞争时，必须通过状态机和事务解决，不能盲目确认订单或释放库存。
8. 情报模块不能修改交易库存、订单、支付或退款数据。
9. 采用模块化单体，禁止在没有架构决策的情况下提前拆分微服务。
10. 使用 Flyway 管理数据库迁移。
11. 使用真实 PostgreSQL 集成测试验证关键事务和并发行为。
12. 不得将未实现的功能标记为完成，不得伪造测试结果或支付成功。

## 后续阶段

### Phase 01 工程骨架与模块治理

- 建立 Maven 多模块结构。
- 建立 API 与 Worker 入口。
- 配置 Spring Boot、Flyway、PostgreSQL、Testcontainers。
- 配置统一异常、参数校验、日志、健康检查。
- 加入 Spring Modulith 模块结构测试。

**验收：** 干净环境可启动；数据库可以从空库迁移；模块依赖测试通过。

### Phase 02 活动、商品与专场

- 建立活动、场次、票档和商品模型。
- 建立专场草稿、配置 Schema、校验和发布版本。
- 实现模块白名单和受控资源引用。
- 实现统一商品列表与票档组件（模块层 facade 与 HTTP 列表端点已实现，7a6bd76；前端页面待建）。
- 实现至少两种专场模板。

**验收：** 同一商品可以出现在多个专场，且不会复制库存；编辑草稿不影响已发布版本。

### Phase 03 库存与订单核心

- 实现库存池、预留、确认、释放和流水。
- 实现订单、订单明细快照和状态机。
- 实现订单幂等键和数据库唯一约束。
- 实现原子库存预留 SQL。
- 实现订单事务、超时释放和异常状态处理。

**验收：** 真实 PostgreSQL 并发集成测试通过；库存余额、预留、已售和流水保持一致。**这是接入真实支付前的硬性门槛。**

### Phase 04 支付、退款与可靠异步处理

- 实现支付渠道接口和测试适配器。
- 实现支付回调验签、去重和状态更新。
- 实现退款状态机。
- 实现 Outbox、Inbox 和 Worker。
- 实现支付、退款与库存对账。

**验收：** 重复回调、支付超时、进程重启、任务重复执行和支付与库存释放竞态测试通过。

### Phase 05 履约与卖家挂牌

- 实现卖家资料、供货审核和挂牌。
- 实现独立票品状态与必要的供货凭证。
- 实现交付流程和异常处理。
- 实现卖家取消、履约失败及争议处理。

**验收：** 未审核供货不能被误标为平台保证可交付；支付成功不自动等于交付成功。

### Phase 06 票务情报与运营完善

- 实现来源适配器、原始观察和标准化。
- 实现价格历史、数据质量检查与来源展示。
- 实现运营后台、审计、监控和告警。
- 实现备份恢复、压力测试和生产部署手册。

**验收：** 情报模块无法修改交易库存；价格来源、更新时间和可信度有明确展示；关键交易指标可观测。

## 优先锁定的三个实现细节

1. **库存模块的写入权必须唯一。** 其他模块只能调用库存接口，不允许直接改库存表。
2. **交易核心先于高级营销。** 先把商品、订单、库存、支付的正确性做扎实，再扩展复杂专场。
3. **先不拆微服务。** 通过 Spring Modulith 和模块化代码约束边界，等情报规模、部署独立性或实际负载确实要求拆分时再决定。
