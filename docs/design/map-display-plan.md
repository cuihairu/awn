# 地图展示方案（todo 156 余项）

- 日期：2026-10-15
- 依据：todo.md 156 余项「地图展示（坐标已有，缺地图服务商选型，挂起待用户裁决，不引第三方不拍板）」；地图之外的地理链已闭环（存储 / 守卫 / 公开读 / web 展示 / 运营配置，8323788 / 75865ae / 01bdff4）
- 现状代码：坐标在 `venue` 表（V19，成对与范围守卫）、场次 geo 由 `EventFacade.sessionVenue` 解析（场次场馆覆盖 → 父活动场馆 → null 不造假坐标）、`SessionView.geo: SessionVenueView | null`、web 端 `apps/web/components/GeoRow.tsx` 只渲染文字行（场馆名 · 城市 · 地址，`geoLine` 组装，全空返回 null）
- 本方案不引第三方、不拍板服务商，只把「能做什么 / 代价 / 待你裁决什么」说清

## 1. 缺口的确切位置

坐标有了，解析有了，公开读有了，运营配置有了。缺的只有一件事：**页面上没有一张能看的位置图**。现在 `GeoRow` 只给一行文字（如「上海大剧院 · 上海 · 黄浦区延安东路」），用户要判断「这是哪个场馆、在哪条街」还得自己去搜。

不需要新能力的位置展示，就能覆盖这个缺口的大半。

## 2. 三条路（按「是否引入第三方」分）

| 方案 | 做法 | 引第三方运行时依赖 | 能力 | 代价 |
|---|---|---|---|---|
| **B（首方静态图）** | 运营在场馆配置里传一张地图图片（PNG，≤2MB，平台存储域白名单），前端在 `<img>` 上叠加定位标记 | **否** | 位置一目了然；不可放大、不可算路线 | 运营多一步制图；坐标仍可用但不驱动图片 |
| A（第三方 JS SDK） | 接入高德 / 腾讯地图 / Mapbox JS SDK，按坐标渲染交互式地图 | **是** | 缩放、定位、路线、实时路况 | 运行时依赖、配额与计费、SDK 合规与审核、首屏包体增加 |
| C（只保留文字） | 不做地图 | 否 | 现状 | 缺口不变 |

### 方案 B 的形态细节

- **一张图 + 一个标记**：图由运营提供（截图拼合、示意图、场馆官方平面图皆可），坐标点由前端按场馆坐标在图上落一个标记。图片本身不必是精确地图，**能指认场馆位置即可**。
- **不承诺地理精度**：图上标记位置由坐标线性映射到图片范围，仅作「大致在这里」提示，文案明示「示意图，非精确地图」——与 3D 座位图方案「舞台位置不声称正确，只标方向提示」同一口径（`docs/design/seatmap-3d-plan.md` §1）。
- **素材红线不变**：地图图片由运营从公开来源取用，平台不提供也不代发任何地图数据 API；不使用场馆照片或 logo 代餐。
- **降级**：图片缺失或加载失败时回退现有 `GeoRow` 文字行，不报错、不白屏。

### 方案 B 的契约改动（预估，已于 2026-10-15 落地，见 §5）

- `venue` 表增 `map_image_url VARCHAR`（可空，受控存储域白名单校验，与供货凭证 / 争议凭证同一 `StorageUrlValidator` 口径）
- `SessionVenueView` 增 `mapImageUrl: string | null`（随现有 geo 解析链路透出，场次场馆覆盖 → 父活动场馆 → null）
- 运营配置面「场次配置」视图加图片 URL 输入（或场馆级配置）
- web 端 `GeoRow` 升级为「图片 + 标记 + 文字行」，无图时行为与现状完全一致

改动面：V25 迁移 + 校验 + 解析链路透出 + 两端渲染，与既有地理链完全同构，无新模块。

## 3. 建议

**走方案 B（首方静态图），不接第三方地图 SDK。**

理由：
1. **不引入第三方运行时依赖**——地图 SDK 意味着配额、计费、合规审核与包体代价，为「让用户看见场馆在哪」这一点不划算。
2. **不拍板服务商**——高德 / 腾讯 / Mapbox 的取舍仍留给你，B 方案不依赖这个决定，先解决缺口；将来拍板 SDK 时 B 的图片字段可作为底图或降级路径并存。
3. **与既有地理链同构**——存储白名单、成对守卫、解析链路、公开读透出都有现成先例（venue 坐标 V19、供货凭证、争议凭证），改动小、风险低。
4. **诚实**——示意图不承诺地理精度，文案明示；真需要路线规划与实时定位时再上 SDK。

## 4. 待你裁决（本方案不动实现）

1. **是否接受「示意图」口径**——接受则 B 方案可直接开工（不引第三方，属我方可自行推进）；
2. **是否需要交互地图**（缩放 / 路线 / 精确到门牌）——需要则必须拍板 SDK（高德 / 腾讯 / Mapbox）并承担第三方依赖；
3. **图片由谁提供**——运营手工制图（B 方案默认），还是要我补一个「按坐标生成静态图」的服务端能力（那才引入第三方瓦片源，等同方案 A）。

裁决 1 为「接受」即可按本方案落 V25 与两端渲染；裁决 2 为「需要」则先出 SDK 选型对比再动实现。

## 5. 落地记录（2026-10-15，巡检单 R1015F 授权）

裁决结果：**① 接受「示意图」口径 → 按方案 B 落地；② 交互地图、③ 供图方式暂不启动**，等真实需求与供图再议（用户事后可推翻）。与预估相比有两处偏离：

1. **迁移号 V26，不是预估的 V25**——`V25__order_attendees.sql` 已被订单实名条目占用，实际迁移为 `V26__venue_map_image.sql`（`map_image_url` + `map_marker_x` + `map_marker_y` 三列）。
2. **标记位置改为运营随图给定，不做坐标线性映射**——§2 预估「图上标记位置由坐标线性映射到图片范围」，但示意图没有地理范围（不是按比例尺截取的地图），经纬度无法换算到图上位置；改为运营在场馆配置里直接给**图上标记百分比**（`map_marker_x/y`，0-100 相对图片左上角，**成对守卫**，与场馆经纬度同一「半截不入库」口径）。非精确口径不变：文案仍明示「位置示意图，非精确地图」。

落地内容：

- 契约：`venue` 三新列；`VenueView` / `SessionVenueView` / api-client `SessionVenueView` 透出 `mapImageUrl` / `mapMarkerX` / `mapMarkerY`（随既有 geo 继承链路：场次场馆覆盖 → 父活动场馆 → null）；`mapImageUrl` 经 `StorageUrlValidator` 域白名单（拒绝 → 400 `VALIDATION_FAILED`）
- 运营面：`PUT /api/v1/admin/venues/{venueCode}` 全量覆盖（缺省即清空；半截坐标 / 半截标记 / 越界一律 400，未知场馆 404 `VENUE_NOT_FOUND`）；admin「场次配置」视图增场馆配置卡片（地理 + 示意图 + 标记，全量覆盖口径在表单上方明示）
- web：`GeoRow` 升级「图片 + 标记 + 文字行」——图片 `onError` 回落文字行；标记半截或越界不渲染；无图行为与现状完全一致；根节点保持 `<span>`（GeoRow 在 `<Link>` 内，须为 phrasing content）
